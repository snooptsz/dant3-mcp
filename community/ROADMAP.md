# Bounded community roadmap

These are contribution opportunities, not assigned work, shipped features or paid commitments. Start with an existing issue or the community contribution form. Do not create synthetic live accounts to complete a task.

| Work item | Useful completion evidence | Boundary |
|---|---|---|
| Onboarding clarity | Reproduce one ambiguity, propose corrected instructions and show the documented command output using safe fixtures or the existing zero-write check. | No registration, credential publication or invented tool/version claims. |
| Portable client fixtures | Offline tests for malformed responses, timeouts and revoked/missing capabilities. | No production data, paid APIs or permissive fallback. |
| Accessibility examples | Keyboard, focus, contrast and small-screen findings with sanitised screenshots and a narrowly scoped improvement. | Preserve current branding; no user names or private messages in screenshots. |
| Safe diagnostic output | Tests that redact credentials, query tokens and sensitive identifiers from example logs. | Use fabricated values; never collect a real secret for a test. |
| Documentation and licence review | Fix a broken link, explain a permission boundary, or identify a dependency licence with its primary source. | No expansion of production scopes or licence replacement. |

Keep the backlog small. Finish or close duplicate proposals before opening another large initiative. Core application, database, moderation, billing, age assurance and legal-policy changes require separate restricted review. Volunteers do not certify the hosted service's compliance.

Successful public code remains public integration work. It does not demonstrate a production deployment or independent account adoption.
